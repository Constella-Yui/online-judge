## 今天最该记住的三句话

1. **异常是控制流的一部分，不是"出错了"的通知。** 它是除了返回值之外，方法往回传信息的第二条通道。
2. **异常由框架在主干上接住，你只负责抛。** Controller 里一行 try-catch 都没有，但异常被处理了——因为这个 `catch` 在 `DispatcherServlet` 里。
3. **重构的定义：对外不变，对内换结构。** 改完之后重名仍然返回 409，只是产出这行的代码从 Controller 挪到了全局处理器。

## 一、热身：破坏性实验 1

**做法**：把 `UserServiceImpl` 上的 `@Service` 删掉 → 启动 → 加回去。

**现象**：启动失败，大意是

```
UnsatisfiedDependencyException: Error creating bean with name 'userController'
  → NoSuchBeanDefinitionException: No qualifying bean of type 'com.oj.service.UserService'
```

**这句话要会读**：Spring 先造 `UserController`，它要一个 `UserService` 参数，但容器里**没找到能当 `UserService` 用的东西**，于是放弃启动。

**收获**：

- `@Service` **不产生任何运行时行为**，它只是往注册表上贴一张纸条：这个类实例化后，登记为 `UserService` 的实现。
- 没有纸条 → 类还是类 → 但容器不知道它存在 → 没人能满足 `UserController` 的构造参数。
- **Spring 宁可启动失败，也不给你一个 null 的 `userService`**。这叫"快速失败"，是它能调试的前提。

> 和 C++ 对照：这相当于编译期的链接错误——一个函数声明了但没定义。**Spring 把这件事推迟到了启动时，所以它得自己检查一遍。**

## 二、从"返回值报错"到"异常报错"

### 改之前

```java
// Service
if (count > 0) return false;
...
return true;

// Controller
boolean ok = userService.register(...);
if (!ok) {
    return Result.fail(ResultCode.CONFLICT, "用户名已存在");
}
return Result.success();
```

### 改之后

```java
// Service
if (count > 0) throw new BizException(ResultCode.CONFLICT, "用户名已存在");

// Controller
userService.register(...);
return Result.success();
```

### 真实理由：`boolean` 只有两个格子

| 将来要加的情况 | 用 `boolean` | 用异常 |
|---|---|---|
| 用户名已存在 | `false` | 抛 |
| 用户名含敏感词 | ← 挤进 `false`，前端只能收到一个笼统提示 | 抛，带自己的话 |
| 需要邮箱验证 | ← 同上 | 抛，带自己的话 |
| 注册功能暂时关闭 | ← 同上 | 抛，带自己的话 |

`boolean` 表达 **两种**结果；业务错误是**无穷多种**。异常能无限扩展，而且**方法签名一个字不用改**。

### 附赠的两个好处

**① Controller 回到了它该有的样子**：把 HTTP 翻译成业务调用，"判断该返回哪个码"不属于它。

改完 `UserController` 里 `import ResultCode` 已经可以删了——它已经**不认识"409"这个概念**了。这就是边界干净的样子。

**② C++ 对照**：竞赛里 `throw` 是拿来做流程控制的（少数派），Java 里是**正统做法**。Java 没有"多返回值"（C++ 可以 `return {a, b}` 或传引用），所以"一个正常结果 + 一个错误"的传递，语言层面就留给了异常。

## 三、BizException 的四个设计决定

```java
@Getter
public class BizException extends RuntimeException {

    private final ResultCode resultCode;

    public BizException(ResultCode resultCode) {
        super(resultCode.getMessage());
        this.resultCode = resultCode;
    }

    public BizException(ResultCode resultCode, String message) {
        super(message);
        this.resultCode = resultCode;
    }
}
```

### 决定 1：为什么是 `RuntimeException`

| | 继承 | 编译器要求 |
|---|---|---|
| 受检异常 | `Exception` | 调用方**必须** `try-catch`，或在签名上 `throws` 一路往上声明 |
| 运行时异常 | `RuntimeException` | **不管** |

用 `Exception`：`register` 要 `throws BizException` → Controller 调它就要也 `throws` → 但 Controller 是 Spring 调的，Spring 不认你的 `throws`……最后只能到处 try-catch。**签名上的 `throws` 会一路传染。**

用 `RuntimeException`：Service 直接扔，Controller 完全不知道，由 `@RestControllerAdvice` 在框架层统一接。

> **面试点**：Spring 的 `@Transactional` **默认只对 `RuntimeException` 回滚**，受检异常不回滚。业务异常用 `RuntimeException` 也是事务上的正确选择。

### 决定 2：为什么要 `super(resultCode.getMessage())`

`getMessage()` 是**父类 `RuntimeException` 的方法**，取的是父类的 private 字段 `detailMessage`。

子类自己**塞不进去**，只有调 `super(...)` 或 `super(msg)` 才能填。

不写 `super(...)` 的话，`RuntimeException` 的无参构造器 `super()` 被隐式调用 → `detailMessage` 是 `null` → `e.getMessage()` 返回 `null` → 前端收到 `{"code":409,"message":null}`。

**所以 `@Getter` 只管 `resultCode`，管不到 `getMessage()`。** 这是两个不同来源的值。

### 决定 3：为什么 `private final`

- `private`：外面不能改
- `final`：构造完就不能再赋值

异常对象造出来之后应该是**不可变的**。否则你可以 `e.setResultCode(ERROR)`，然后它在往上抛的路上被谁改了你都不知道。

### 决定 4：为什么存 `ResultCode` 而不是存 `int code`

存 `int` 也能用，但 `409` 会在枚举里写一遍、在异常里存一遍，**两处可能不一致**。

存枚举 = **单一事实来源**。改 409 的含义只改一个地方。

## 四、GlobalExceptionHandler：注解与机制

### 三个注解

**`@Slf4j`** —— Lombok 往类里塞：

```java
private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);
```

不写这个注解，`log` 就是红色未定义符号。

**`@RestControllerAdvice`** —— 其实是三样东西：

```java
@ControllerAdvice   // 我是全局的，管所有 Controller
@ResponseBody       // 方法返回值不走视图解析，直接序列化成 JSON
```

> 只写 `@ControllerAdvice` 会怎样：Spring 把返回的 `Result` 当成**视图名**去找模板 → 前端收到 404 或找不到视图。**返回值是对的，但传不出去。**

**`@ExceptionHandler(X.class)`** —— 标记"我接 X 及其子类"。**单独放在普通类里没有任何作用**，必须配合类上的 `@ControllerAdvice` 才会被注册进"异常 → 方法"对照表。

### 它凭什么能接住异常

```
Controller 里 throw BizException
        ↓
DispatcherServlet 的 catch 块
        ↓
遍历 HandlerExceptionResolver（@ControllerAdvice 是其中一环）
        ↓
查表：BizException → handleBiz
        ↓
反射调用，返回值由 @ResponseBody 序列化成 JSON 写回
```

**你一行 try-catch 都没写，但它被接住了**——因为拦截发生在框架层，不在你的代码里。

这就是昨天那句"你不在控制流主干上"最具体的证据。**注解的法力不是它自己变法，是有人（`DispatcherServlet`）早就在那条路上等着了。**

## 五、匹配规则和三个坑

### 坑 1：按"最具体"，不按书写顺序

把 `handleOthers(Exception.class)` 挪到文件第一行也没用。Spring 算继承距离，`BizException` 比 `Exception` 近。

**反过来最要命**：如果漏了 `handleBiz`，`BizException` 会掉进兜底 → 变成 **500**。明明抛的是 409，前端收到 500，然后你会去查数据库。

### 坑 2：它接不到 404

访问不存在的 URL 时，Spring 默认**不抛异常**，直接由 `BasicErrorController` 返回 `{"timestamp":...}`。

想接管要开两个配置（**今天没开，等写拦截器时一起处理**）：

```yaml
spring:
  mvc:
    throw-exception-if-no-handler-found: true
  web:
    resources:
      add-mappings: false
```

### 坑 3：`@RequestParam` 的校验不走这里

`MethodArgumentNotValidException` **只为 `@RequestBody` + `@Valid` 服务**。

将来 `@RequestParam @Min(1) Integer page` 校验失败，抛的是 `ConstraintViolationException`，要单独写个方法。**D5 做分页时会遇到。**

### 另外两个小点

**`log.error` 的两个参数是约定**：

```java
log.error("未捕获异常", e);
//        第 1 个：正文    第 2 个：异常对象 → 自动附加完整堆栈
```

写成 `log.error(e.getMessage())` 就只有一行字，**没有类名、没有行号**，等于白记。

**为什么 "请求体不是 JSON" 用 `log.warn` 不用 `log.error`**：这是客户端的错，不是系统的错，不该污染 error 日志。

## 六、重构实录：boolean → void

| 位置 | 原 | 改 |
|---|---|---|
| `UserService` 签名 | `boolean register(...)` | `void register(...)` |
| `UserServiceImpl` 查重 | `return false;` | `throw new BizException(CONFLICT,"用户名已存在");` |
| `UserServiceImpl` catch | `return false;` | `throw new BizException(CONFLICT,"用户名已存在");` |
| `UserServiceImpl` 末尾 | `return true;` | **删除** |
| `UserController` | `boolean ok = ...; if(!ok){...}` | 一行调用 + `return Result.success();` |

### 一个可复用的方法：让编译器导航

改完接口之后**不要自己去找还有哪里要改**，直接编译。

`UserController` 里那句 `boolean ok =` 立刻变红——**编译器把所有受影响的调用点都列出来了**。

这是 Java 静态类型在重构时最大的价值。C++ 也一样，但 Java 的编译是"全量、必过"的，不像 C++ 那样容易漏掉某个没被实例化的模板。

## 七、代码存档

### `common/BizException.java`

```java
package com.oj.common;

import lombok.Getter;

/**
 * 业务异常：Service层发现"业务上不成立"时抛出
 * 由GlobalExceptionHandler统一翻译Result返回前端
 */
@Getter
public class BizException extends RuntimeException {

    private final ResultCode resultCode;

    public BizException(ResultCode resultCode) {
        super(resultCode.getMessage());
        this.resultCode = resultCode;
    }

    public BizException(ResultCode resultCode, String message) {
        super(message);
        this.resultCode = resultCode;
    }
}
```

> 注意：构造器参数名和字段名撞了，**必须写 `this.`**。不写的话那行变成"参数赋值给自己"，`final` 字段从头到尾没人赋值 → 编译报 `variable resultCode might not have been initialized`。

### `common/GlobalExceptionHandler.java`

```java
package com.oj.common;

import lombok.extern.slf4j.Slf4j;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

/**
 * 全局异常处理：Controller 链路上抛出的所有异常都在这里变成 Result
 */
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    /* 1. 业务失败（Service 主动 throw 的） */
    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException e) {
        return Result.fail(e.getResultCode(), e.getMessage());
    }

    /* 2. @Valid 校验未通过，取第一条错误信息 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValidation(MethodArgumentNotValidException e) {
        FieldError first = e.getBindingResult().getFieldError();
        String msg = (first == null) ? ResultCode.PARAM_ERROR.getMessage()
                                     : first.getDefaultMessage();
        return Result.fail(ResultCode.PARAM_ERROR, msg);
    }

    /* 2 补充：请求体不是合法 JSON（D3 那个 400 就是它） */
    @ExceptionHandler(HttpMessageNotReadableException.class)
    public Result<Void> handleUnreadable(HttpMessageNotReadableException e) {
        log.warn("请求体解析失败：{}", e.getMessage());
        return Result.fail(ResultCode.PARAM_ERROR, "请求体格式错误");
    }

    /* 3. 兜底 */
    @ExceptionHandler(Exception.class)
    public Result<Void> handleOthers(Exception e) {
        log.error("未捕获异常", e);
        return Result.fail(ResultCode.ERROR);
    }
}
```

### `service/impl/UserServiceImpl.java`（改动部分）

```java
@Override
public void register(String username, String rawPassword, String nickname) {
    // 1. 查重
    Long count = userMapper.selectCount(
            new LambdaQueryWrapper<User>().eq(User::getUsername, username));
    if (count > 0) {
        throw new BizException(ResultCode.CONFLICT, "用户名已存在");
    }
    // 2. 组装实体，密码哈希
    User user = new User();
    user.setUsername(username);
    user.setPassword(passwordEncoder.encode(rawPassword));
    user.setNickname(nickname);
    // 3. 数据库防线
    try {
        userMapper.insert(user);
    } catch (DuplicateKeyException e) {
        throw new BizException(ResultCode.CONFLICT, "用户名已存在");
    }
}
```
