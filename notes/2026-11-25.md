## 一、开工前：先验环境

启动应用报 `Port 8080 was already in use`，是昨天跑的进程没关。杀掉重启之后，`curl` 全返 **500**。

**原因：SSH 隧道关了。** `ssh -N -L 3306:...` 是跑在某个终端窗口里的，**窗口一关，隧道就断**。数据库连不上 → `selectCount` 抛异常 → 掉进兜底 → 500。

### 两条纪律

**① 开工第一件事查环境，不是写代码。**

```bash
netstat -an | grep 3306    # 没输出 = 隧道死了
```

代码报错和数据库连不上，在 `curl` 上都表现为"不对"，但原因一个在你的文件里、一个在你的窗口里。

**② 隧道单独一个窗口，加上心跳。**

```bash
ssh -N -o ServerAliveInterval=30 -L 3306:127.0.0.1:3306 root@47.243.5.119
```

`-N` = 只转发不执行命令，所以它**不会出现提示符、不会打印任何东西**。没输出就是正常。

### 一个诊断技巧

返回 `{"code":500,...}` 而不是 Spring 的 `{"timestamp":...}`，说明**你的 `GlobalExceptionHandler` 正在工作**，是兜底那档接住的。也就是说：**问题不在异常处理，而在抛出来的异常不是 `BizException`。**

此时唯一的动作是去看日志，找这一行：

```
ERROR ... GlobalExceptionHandler : 未捕获异常
```

它下面那一坨堆栈的第一行就是答案。

> 昨天写 `log.error("未捕获异常", e)` 时坚持带第二个参数，就是为了这一刻。只写 `e.getMessage()` 的话，现在手里只有一句没头没尾的话。

## 二、四轮验证，和一次"假通过"

### 第一次跑：四条全 200

```
{"code":200,"message":"成功","data":null}
```

看起来像"校验失效"。实际情况是：**代码还没改**。`RegisterRequest` 上一个注解都没有。

| 现象 | 原因 |
|---|---|
| 校验**没有生效** | 代码写了，但没被激活（没重启 / 依赖缺失 / 扫描不到） |
| 校验**不存在** | 代码根本没写 |

两者的 `curl` 输出**一模一样**。这就是为什么"改动前后的对照"是验证的唯一标准：

> **先跑一次坏的，再改，再跑一次好的。** 只跑后面那次，你永远不知道自己在验证什么。

而且这四条 200 有个副作用：**三个非法用户真的进库了**。数据库不会替你拦，`password` 列存的是合法密文，哪怕原文是 `123`。

### 第二次跑：四条都对了

| 请求 | 结果 |
|---|---|
| `username: ""` | 400 `用户名长度需在4-32之间` |
| `username: "ab"` | 400 `用户名长度需在4-32之间` |
| `password: "123"` | 400 `密码长度需在6-32之间` |
| 合法新用户 | 200 |
| `username: "test01"`（已存在） | 409 |

第 1 条报的是长度不是"不能为空"——见下一节，这不是 bug。

### 一个 30 秒的观察

三条 400 的请求，**控制台里一条 SQL 都没有**（`log-impl: StdOutImpl` 会打印每条 SQL）。

因为 `@Valid` 校验发生在 `DispatcherServlet` 调用 Controller **之前**，非法请求根本进不到 Service，连数据库都没碰。

**校验的位置，决定了它挡住了多少东西。** 挂在 Controller 参数上，挡住整条调用链；写在 Service 里，前面已经跑完了。

## 三、@Size 为什么放过 null

这是今天最反直觉的一点。

| 输入 | `@NotBlank` | `@Size(4,32)` | 结果 |
|---|---|---|---|
| `null`（字段不存在） | ❌ | ✅ **通过** | 只有 `@NotBlank` 能拦 |
| `"   "`（全是空格） | ❌ | ❌ | 两条都拦 |
| `"ab"` | ✅ | ❌ | 只有 `@Size` 能拦 |
| `""`（空串） | ❌ | ❌ | 两条都拦 → 报哪条不固定 |

**`@Size` 把 `null` 视为合法**（"没有值"和"长度不够"是两回事）。所以：

> **`@NotBlank` 不能省。** 省了之后 `null` 会一路穿过 `@Size` 进 Service → `selectCount` 里 `username = null` → 查重永远查不到 → `insert` 撞上非空列 → 500。
> **少一条校验，400 就漂移成 500。**

### 为什么空串报的是长度错误

`""` 同时违反两条约束，**"哪条先报"没有任何规范保证**，由 Hibernate Validator 内部决定。

想让它说人话，改文案就行，不用动结构：

```java
@Size(min = 4, max = 32, message = "用户名长度需在 4-32 之间（不能为空）")
```

而且这句提示**逻辑上没错**：空串长度 0，确实不在 4-32 之间。

## 四、三件工具各管什么

到目前 12 个 Java 文件、一条跑通的注册链路，三件工具的分工其实已经能看清了。

### 一句话版

| 工具 | 一句话 |
|---|---|
| **Java** | 管**名词**：有哪些概念、它们是什么形状、能发出什么信号 |
| **Spring Boot** | 管**动词的连接**：谁 new 谁、请求怎么走到方法、结果怎么回去 |
| **MySQL** | 管**记忆**：进程重启之后还记得什么 |

### 详细一点

**Java —— 编译期的那一层**

它一个字都不会帮你"运行"，但决定了你能怎么表达：

| 机制 | 在这个项目里的体现 |
|---|---|
| 类型系统 | 改 `boolean` → `void` 之后，**编译器替你找出了所有调用点**（重构时最大的价值） |
| 接口 + 多态 | `UserService` 声明"能做什么"，`UserServiceImpl` 决定"怎么做" |
| 异常 | 除返回值之外的**第二条信息通道**，可以无限扩展而签名不变 |
| 没有多返回值 | 所以"一个正常结果 + 一个错误"只能靠异常或包装类来传 |
| 注解 | 纯粹的**元数据，本身不带任何行为**。它的法力全在于"有人去找它" |
| 包 = 目录 | `package com.oj.dto;` 和物理路径必须一致 |

> 关键理解：**注解不执行任何代码**。`@NotBlank` 之所以能拦住请求，是因为 `DispatcherServlet` 在调 Controller 之前，会去找一个 Validator 读这些注解。**注解是标签，干活的是那个看标签的人。**

**Spring Boot —— 运行时的那一层**

一条 `curl` 到你的方法之间，它替你走完了这些：

```
curl
 → Tomcat（Boot 内嵌）          TCP 字节 → HttpServletRequest
 → DispatcherServlet            按 URL + 方法找 @PostMapping
 → 参数绑定 / @Valid            JSON → RegisterRequest，并校验
 → UserController               ← 你写的第 1 个节点
 → UserService / Impl           ← 你写的第 2 个节点
 → UserMapper（MP 生成的代理）   ← 你写的第 3 个节点（只有接口）
 → MySQL
```

返回时再反过来：对象 → Jackson → JSON → HTTP 响应。

**这条链上你只写了三个节点，其余全被别人的代码串起来了。** 12 个文件能撑起一个完整服务，原因就在这里。

Spring 与 Spring Boot 的区别也值得记：

- **Spring** 提供容器（IoC）、Web 管线、AOP 这些**能力**
- **Spring Boot** 把"装配"变成"默认装好"：起步依赖（`starter-web` 带进 Tomcat）、自动配置（有 MySQL 驱动就自动配数据源）、内嵌服务器（不用装 Tomcat）

**MySQL —— 跨进程的那一层**

内存里的一切都是暂时的。`User` 对象在请求结束时就被回收了，只有数据库里的行能活到下一个请求、下一次重启。

它还有一个别人给不了的东西：**硬保证**。Service 里的查重可以被绕过（新入口忘了写），唯一索引不会。代价是它只会给你一个冷冰冰的 `DuplicateKeyException`。

### 所以三者的关系

```
Java      定义"数据长什么样"、"错误怎么表达"
  ↓
Spring    把外部世界（HTTP）和你的代码接起来
  ↓
MySQL     把状态留在进程之外
```

**缺一层会怎样**：

| 缺了 | 后果 |
|---|---|
| Java 的类型/异常 | 每层都得手写 if-else 传递错误，改一处漏一处 |
| Spring | 你要自己写 servlet、自己 new 对象、自己把 JSON 转成对象 |
| MySQL | 应用一重启，所有用户消失 |

## 五、文件是按什么思路长出来的

这是今天真正要回答的问题：**不看 AI，怎么自己想到要建哪些文件？**

### 5.1 现在有什么

```
com/oj
├── OnlineJudgeApplication.java       启动类：容器的入口
├── common/                            横切：所有接口共享
│   ├── Result.java                    统一外壳 code/message/data
│   ├── ResultCode.java                错误码字典（单一事实来源）
│   ├── BizException.java              "业务上不成立"的信号
│   └── GlobalExceptionHandler.java    异常 → Result 的翻译点
├── controller/                        对外边界
│   ├── HelloController.java
│   └── UserController.java
├── dto/                               入参形状
│   └── RegisterRequest.java
├── entity/                            表形状
│   └── User.java
├── mapper/                            数据库边界
│   └── UserMapper.java
└── service/
    ├── UserService.java               能做什么
    └── impl/UserServiceImpl.java      怎么做
```

### 5.2 心法：文件不是"想"出来的，是"走"出来的

别对着空目录 brainstorm 文件名。**拿一条请求，从浏览器一路走到磁盘，数它跨了几个世界。**

```
① 网络世界      一行 HTTP 文本
       ↓  跨边界 → 需要翻译 → controller/ + dto/
② 业务世界      Java 对象 + 规则
       ↓  跨边界 → 需要翻译 → mapper/ + entity/
③ 数据库世界   一行行的列
```

**每跨过一次边界，就要一次"翻译"，每次翻译落一个文件。** 这不是打比方，这是这套分层唯一的成因。

- HTTP 文本 ↔ Java 对象 → `Controller` 负责翻译入口，`dto` 负责描述入口的形状
- Java 对象 ↔ 数据行 → `Mapper` 负责翻译动作，`entity` 负责描述行的形状

**没有跨越边界的代码，就不需要文件。** 比如 `Impl` 里的 `if (count > 0)` —— 它只是在业务世界里挪了一下，所以它没有自己的文件。

### 5.3 四种形状（本节最重要）

同一条数据，在四个地方长得**必须不一样**：

| 形状 | 类 | 长得像 | 为什么不能合并 |
|---|---|---|---|
| **表形状** | `entity/User` | 表有什么列就有什么字段，含 `password`、`role`、`status` | 它跟着 schema 走 |
| **入参形状** | `dto/RegisterRequest` | 只有 `username/password/nickname` | 客户端**不该能传** `role`。能传就能自己提权成管理员 |
| **出参形状** | `vo/UserVO`（待建） | 只有能见人的字段，**没有 password** | 带 password 出去就是泄密 |
| **统一外壳** | `common/Result<T>` | `code / message / data` | 前端要一个固定的信封，不该每个接口一种格式 |

这三条不是风格偏好，是**三个不同的信任方向**：

- **dto 防的是客户端**：它给你的字段越少，它就越不能乱来
- **vo 防的是你自己**：表里加了 `password_reset_token` 这种列，你不改 vo 它也不会漏出去
- **entity 是内部的**：它只在你和数据库之间流动

> **一条硬规矩：`entity` 永远不该出现在 Controller 的返回类型里。**
> 这就是 `vo` 存在的全部理由。不是"分层好看"，是"多一个类，少一次泄密"。

### 5.4 四个问题 → 文件清单

拿到任何一个新需求，按顺序问这四句，文件清单会自己掉出来：

**Q1. 它属于哪个"资源"？**
（user / problem / submit / judge …）
→ 资源相同 → 往已有 `XxxController` **加方法**；资源不同 → **新建** `XxxController`

**Q2. 客户端要传什么？和表长得一样吗？**
→ 不一样（少了列、要分组、有嵌套）→ 新建 `XxxRequest`
→ 完全一样且只有一两个字段（比如只有 `id`）→ **不用建**，用 `@PathVariable`

**Q3. 要返回什么？里面有敏感列或冗余列吗？**
→ 有 `password`、`email` 这种 → 新建 `XxxVO`
→ 返回的只是一个"做完了"的信号（注册、删除）→ 用 `Result<Void>`，**不建 VO**

**Q4. 要读写数据库吗？**
→ 表已存在 → **复用** `entity` + `mapper`
→ 新表 → 新建 `entity` + `mapper`（MyBatis-Plus 自动给 CRUD）

**外加两条：**

**Q5. 有"业务上不成立"的情况吗？** → `throw new BizException(...)`，缺码就往 `ResultCode` 加一行
**Q6. 这个东西会被多个资源共用吗？** → 会 → 放 `common/`（将来还会有 `config/`、`util/`、拦截器）

### 5.5 用这个方法推一遍还没写的三步

**③ 登录**

| 问题 | 回答 | 产出 |
|---|---|---|
| Q1 资源 | user | 往 `UserController` 加方法，**不新建 Controller** |
| Q2 入参 | 只有 username + password，没有 nickname | **新建 `LoginRequest`** |
| Q3 出参 | 只要一个 token，绝不是 User | **新建 `LoginVO`** |
| Q4 读库 | 表已存在 | 复用 `UserMapper` |
| Q5 失败 | 用户不存在 / 密码错 | 复用 `BizException` + `UNAUTHORIZED` |

→ **2 个新文件 + 1 个新方法。**

**④ 查用户 `GET /api/user/{id}`**

| 问题 | 回答 | 产出 |
|---|---|---|
| Q1 资源 | user | 加方法 |
| Q2 入参 | 就是路径上的 id | 用 `@PathVariable`，**不建 Request** |
| Q3 出参 | 含 password → 必须脱敏 | **新建 `UserVO`** |
| Q4 读库 | 已存在 | 复用 mapper |
| Q5 失败 | 用户不存在 | `BizException(NOT_FOUND)` |

→ **1 个新文件。**

**结论：③ + ④ 只要 3 个新文件。** 这不是我拍脑袋给的规格，是同一条路径推出来的唯一结果。等你明天真写的时候，应该能自己推出这个清单——**这就是"不用问 AI 也能想到"的样子。**

### 5.6 命名即位置

后缀不是啰嗦，是把"位置"编进名字里：

| 看到名字 | 立刻知道 |
|---|---|
| `UserVO` | 它是出参，不能带 password |
| `RegisterRequest` | 它只活在 Controller 的参数上，改了它不影响别处 |
| `UserServiceImpl` | 业务规则在这里，不在这里的方法说明它不属于 User |
| `UserMapper` | 只有它碰 SQL |

一个从没见过你代码的人，靠名字就能找到东西在哪一节。**文件名的价值不在"叫什么"，在"它暗示自己不该出现在哪"。**

### 5.7 什么时候**不该**新建文件

抽象是有成本的，下面是三条刹车：

1. **只有一个调用方，不要抽接口。** 等第二个调用方出现再抽——那时候你才知道真正的共同点是什么。
   （例外：`Service` 是接口 + Impl，这已经成了 Java 后端的肌肉记忆，留着，将来加事务/代理也靠它。）
2. **不要为了"分层完整"建空包、空类。** 现在没有 `config/`、`vo/` 是正常的——没有需求就没有文件。
3. **工具方法先放就近的类里**，同一个逻辑出现第三次，再抽 `util`。

> 反过来说：**"不新建文件"同样是设计决定。** 往 `UserController` 加方法还是新建一个 Controller，依据是"是不是同一个资源"，不是"代码长短"。

## 六、纵深防御：一件事有好几道防线

这个项目里，校验其实出现了两次：

| 目标 | 业务层（人话） | 数据库（硬保证） |
|---|---|---|
| 用户名非空、长度 ≤32 | `@Valid` → 400 「用户名不能为空」 | `NOT NULL` + `varchar(32)` |
| 用户名唯一 | Service 查重 → 409 「用户名已存在」 | `username` 上的唯一索引 → `DuplicateKeyException` |
| 密码安全 | 长度 ≥6 | BCrypt 哈希存储 |

**为什么两道都要：**

- 业务层**能给出好提示，但可能被绕过**（比如将来加一个"后台导入用户"的入口，忘了查重）
- 数据库**不会漏，但只会给你一个冷冰冰的约束冲突**

> 分工是：**数据库兜底，业务层负责把错误翻译成人话。**
> 这也是为什么 `UserServiceImpl` 里那个 `try/catch (DuplicateKeyException)` 不能删——它翻译的就是"最后一道防线被撞响"的那一声。

## 七、代码存档

### `dto/RegisterRequest.java`

```java
package com.oj.dto;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import lombok.Data;

@Data
public class RegisterRequest {

    @NotBlank(message = "用户名不能为空")
    @Size(min = 4, max = 32, message = "用户名长度需在4-32之间")
    private String username;

    @NotBlank(message = "密码不能为空")
    @Size(min = 6, max = 32, message = "密码长度需在6-32之间")
    private String password;

    @Size(max = 32, message = "昵称最长 32 个字符")
    private String nickname;
}
```

> `nickname` 只加 `@Size`，**绝不能加 `@NotBlank`**——加了之后，原来不带 nickname 的注册请求会从 409/200 变成 400，**一个本来合法的请求被新校验掐死了，这叫破坏性变更**。
> 加校验前先问：**原来哪些请求是能过的？我会不会把它们拦死？**

### `controller/UserController.java`

```java
package com.oj.controller;

import com.oj.common.Result;
import com.oj.dto.RegisterRequest;
import com.oj.service.UserService;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/user")
@RequiredArgsConstructor
public class UserController {

    private final UserService userService;

    @PostMapping("/register")
    public Result<Void> register(@Valid @RequestBody RegisterRequest req){
        userService.register(req.getUsername(),req.getPassword(),req.getNickname());
        return Result.success();
    }
}
```

> `@Valid` 加在**方法参数**上，不是类上。它的语义是"调用这个方法时，把这个参数校验一遍"——它是动作，不是标签。
