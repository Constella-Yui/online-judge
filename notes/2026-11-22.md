## 一、SQL 概念速通

### 1.1 用 C++ 的话说

| SQL | C++ 里最接近的 | 差别 |
|---|---|---|
| 表 (table) | `struct` 的数组 | 在磁盘上，能装几亿条 |
| 行 (row) | 数组里的一个实例 | 一条记录 |
| 列 (column) | `struct` 的成员 | 有类型约束 |
| 主键 (PRIMARY KEY) | 唯一且自动递增的下标 | 不能空、不能重复 |
| **索引 (INDEX)** | **排序数组 + 二分** | **本质相同** |
| 外键 (FOREIGN KEY) | 指向另一张表的引用 | 数据库帮你校验有效性 |
| UNIQUE | `set` | 同列不能重复 |

### 1.2 数据类型速查（只记这 8 个）

| 类型 | 装什么 | 例子 |
|---|---|---|
| `BIGINT UNSIGNED` | 0 ~ 1.8×10¹⁹ | 所有 `id` |
| `INT` | ±21 亿 | 毫秒、内存 MB、计数 |
| `TINYINT` | -128~127（UNSIGNED 则 0~255） | 状态码、难度、role |
| `VARCHAR(n)` | 变长，n 是**字符数**上限 | `username VARCHAR(32)` |
| `CHAR(n)` | 定长 | `alias CHAR(2)` |
| `TEXT` / `MEDIUMTEXT` | 64 KB / 16 MB | 说明 / 题面和代码 |
| `JSON` | 结构化数据 | 样例数组 |
| `DATETIME` | 日期时间 | `create_time` |

### 1.3 关系怎么落到表上

| 关系 | 例子 | 怎么建 |
|---|---|---|
| **1:1** | 用户 ↔ 用户详情 | 少见，直接合成一张表 |
| **1:N** | 一道题 → 多个测试点 | 外键放在**多**的那一边 |
| **M:N** | 比赛 ↔ 题目 | **必须建中间表** |

**M:N 为什么必须建中间表？** 一行只能放一个 `problem_id`，而一场比赛有很多题；反过来 `problem` 也放不下一个 `contest_id`。**没有地方存"这一对"**，只能单独开一张表，每行存一对。

## 二、MySQL 的 schema 到底是什么

> 今天在 IDEA 里看到「当前架构未设置」这句话，卡了一下。这里说清楚。

### 2.1 两个常见含义

**① 逻辑容器 / 命名空间**：MySQL 里 `SCHEMA` 和 `DATABASE` **基本是同义词**。

```sql
CREATE SCHEMA shop;      -- 等价于
CREATE DATABASE shop;
```

**② 数据库对象的结构定义**：表有哪些字段、类型、索引、约束——也就是常说的「表结构」。

### 2.2 作为「库」的作用

1. **组织对象，避免命名冲突**：`shop.users` 和 `blog.users` 可以共存
2. **权限隔离**：`GRANT SELECT ON shop.* TO 'reader'@'%';`
3. **隔离不同环境/项目/租户**：`app_dev` / `app_prod` / `tenant_a`
4. **方便备份迁移**：`mysqldump shop > shop.sql`
5. **设置默认 schema**：`USE shop;` 之后 `SELECT * FROM users` 等价于 `shop.users`

> 我们的项目就是 `oj` 这一个库。

### 2.3 作为「表结构设计」的作用

定义字段、类型、长度；主键、外键、唯一约束；索引。它同时是**数据一致性保证**和**开发文档**。

### 2.4 初学者注意

- MySQL 中 **schema ≈ database**，不像 Oracle 那样「用户即 schema」
- 说「建一个 schema」通常指「建一个数据库」；说「设计 schema」通常指「设计表结构」
- schema 本身不直接提升性能，但**合理的库表划分和表结构设计会影响管理和性能**

## 三、ER 图：设计表之前先画图

### 3.1 是什么

**ER 图 = Entity-Relationship Diagram，实体-联系图。** 描述：业务里有哪些对象、对象有哪些属性、对象之间有什么关系。

> **ER 图 = 实体 + 属性 + 联系 + 基数**
> **数据库 schema = 根据 ER 图细化出的表、字段、主键、外键、索引**

### 3.2 基本元素

| 元素 | 含义 | 传统画法 |
|---|---|---|
| **实体 Entity** | 用户、商品、订单、题目 | 矩形 |
| **属性 Attribute** | `id`、姓名、注册时间 | 椭圆（主键加下划线） |
| **联系 Relationship** | 用户「提交」代码 | 菱形 |
| **基数 Cardinality** | `1:1` / `1:N` / `M:N` | 连线上标注 |

### 3.3 两种画法

- **Chen 符号**：矩形实体 + 椭圆属性 + 菱形联系。适合**教学和理解概念**。
- **鸦脚符号 Crow's Foot**：矩形表 + 表内列字段 + 端点"鸦脚"表示多端。工程中更常见，**更接近最终表结构**。

### 3.4 画图七个步骤

```
① 明确业务范围 → ② 找实体 → ③ 列属性 → ④ 定主键
→ ⑤ 找联系并标基数 → ⑥ 处理多对多 → ⑦ 转成表结构
```

### 3.5 多对多必须拆中间表

文章 ↔ 标签是多对多：

```sql
post_tag (
  post_id,
  tag_id,
  PRIMARY KEY (post_id, tag_id)
)
```

### 3.6 七个常见错误

1. 把 ER 图直接当最终表结构
2. 多对多不拆中间表
3. 一对多**外键放错边**（应放在"多"的一侧）
4. 忘记主键
5. 把属性画成实体
6. 联系上乱加属性
7. （今天新增的）**把一对多的"多"塞进"一"的一个字段里** —— 见 §六 6.2

### 3.7 常用工具

draw.io / diagrams.net、Mermaid、MySQL Workbench、PlantUML、ProcessOn

## 四、索引：今天唯一真正的难点

### 4.1 复合索引的物理顺序

建 `(problem_id, status)`，等于把数据**先按 `problem_id` 排序，相同的再按 `status` 排序**：

```
(problem_id=1, status=AC)     ← 最前
(problem_id=1, status=WA)
(problem_id=2, status=AC)
(problem_id=2, status=TLE)
```

因为有序，才能二分。所以：

| 查询 | 能用这个索引吗 | 原因 |
|---|---|---|
| `WHERE problem_id=1` | ✅ | 按 problem_id 有序 |
| `WHERE problem_id=1 AND status=AC` | ✅ | 定位 1 后在区间内再二分 |
| `WHERE status=AC` | ❌ | AC 散落各处，**不连续**，二分不了 |
| `ORDER BY problem_id, status` | ✅ | 索引本身是这个顺序，免排序 |

**最左前缀原则**：复合索引 `(A, B)` 只能加速**以 A 开头**的查询。

推论：
- `(A, B)` 和 `(B, A)` 是**两个不同的索引**
- 有 `(A, B)` 就不必再建 `(A)`（前缀被覆盖）
- 有 `(A)` 仍然需要 `(A, B)`（覆盖不到 B）

### 4.2 索引不是免费的

每个索引都是一棵额外的树。每次 `INSERT` / `UPDATE` / `DELETE` 都要同步维护，还占磁盘。

> **建索引的唯一标准：能写出它加速的那条 SQL。写不出来 = 别建。**

## 五、沙箱实验：亲手跑出来的六个结论

**实验环境**：`sandbox.t(id, a, b)`，10 万行。`a = n % 1000`（1000 个不同值），`b = n % 7`（7 个不同值）。

### 结论 1 · `type` 的五种值

| `type` | 含义 | 扫多少 |
|---|---|---|
| `ALL` | 全表扫描 | 全部行 |
| `index` | **全索引扫描** | 全部行（只是换了扫描对象） |
| `range` | 范围扫描 | 一段区间 |
| `ref` | 等值查找 | 一小撮 |
| `const` | 主键/唯一索引等值 | 最多一行 |

### 结论 2 · `ALL` 变 `ref`，`rows` 从 10 万掉到 100

```sql
EXPLAIN SELECT * FROM t WHERE a = 500;
-- 建索引前：type=ALL, possible_keys=空, key=空, rows=100320
CREATE INDEX idx_a ON t(a);
EXPLAIN SELECT * FROM t WHERE a = 500;
-- 建索引后：type=ref, possible_keys=idx_a, key=idx_a, rows≈100
```

**`O(n)` 变 `O(log n)`，肉眼看得到。**

### 结论 3 · `possible_keys` 空 = 索引根本不存在

今天最有用的一条**诊断技巧**。

| 情况 | `possible_keys` | `key` | 说明 |
|---|---|---|---|
| **索引不存在** | **空** | 空 | MySQL 压根不知道有这个索引 |
| 索引存在但优化器不选 | 有值 | 空 | 代价模型算下来不划算 |
| 索引被使用 | 有值 | 有值 | 正常 |

> 跑完 `CREATE INDEX` 去看 `EXPLAIN`，看到 `possible_keys` 空——
> **不是"优化器不选"，是那句话根本没执行。**
> 诊断方法：`SHOW INDEX FROM t;`

### 结论 4 · `type=index` 不是「走了索引」

关掉跳扫后 `WHERE b = 3`：

```
1,SIMPLE,t,,index,,idx_ab,8,,100320,10,Using where; Using index
```

- `possible_keys` **空** → 没有任何索引能用于这个 WHERE
- `key=idx_ab` → 但它**碰**了这个索引
- `rows=100320` → **还是扫了全部**

**为什么选 `index` 不选 `ALL`？** 因为 `idx_ab` 是覆盖索引，比表窄（InnoDB 聚簇索引每行多 13 字节隐藏字段：6 字节事务 ID + 7 字节回滚指针）。**反正都要扫完，扫窄的。**

> **判断索引有没有用，看 `rows`。看 `key` 会被骗。**

### 结论 5 · Skip Scan：最左前缀的例外（MySQL 8.0.13+）

```sql
EXPLAIN SELECT * FROM t WHERE b = 3;
-- 跳扫开启：type=range, key=idx_ab, rows=14331
--           Extra: Using where; Using index for skip scan
```

**原理**：不能一次二分定位 `b=3`，但可以把 `a` 的 **1000 个不同值挨个数过去**，在每段里找 `b=3`。1000 次小查找 < 10 万行全表扫，划算。

**什么时候不管用？** 前导列基数高时。`problem_id` 有上万个不同值，跳扫要分上万组，代价爆炸，优化器直接放弃。

```sql
SET SESSION optimizer_switch = 'skip_scan=off';
EXPLAIN SELECT * FROM t WHERE b = 3;    -- 回到 type=index, rows=全表
SET SESSION optimizer_switch = 'skip_scan=on';
```

> **结论：最左前缀仍是设计复合索引的第一原则。Skip Scan 是优化器的补救，不能当设计依据。**

### 结论 6 · `Using index` = 覆盖索引

`Extra` 里出现 `Using index`，说明**查询要的列全在索引里，不用回表**。

InnoDB 的二级索引会自动带上主键，所以 `idx_ab` 实际存的是 `(a, b, id)`。表 `t` 只有三列，`SELECT *` 被完全覆盖。

> 真实业务里 `SELECT *` 通常要回表，所以跳扫未必划算——**测试表要留意列数**。

### 附 · 递归 CTE 的坑

```sql
SET SESSION cte_max_recursion_depth = 200000;   -- 默认只有 1000
```

不先放宽，插 10 万行会报 `ERROR 3636: Recursive query aborted after 1001 iterations`。

## 六、user 表设计：五个决策

完整内容见 `docs/er-design.md` §1，这里只留骨架。

### 6.1 表职责

> **`user` 回答：这个人是谁、能不能登录、有什么权限、一共做了多少题。**

**曾写错**：把"在什么时间点给哪个题目做了提交"也写进去了——那是 `submission` 的职责。

### 6.2 最大的错误：把 `submission` 当成 `user` 的字段

一个用户可能提交 500 次。塞进一个字段会怎样：

| 问题 | 后果 |
|---|---|
| 行有多长 | 几 MB，一个"用户"占半页纸 |
| 查昵称要读多少 | **被迫读全部 500 条提交** |
| 怎么查"最近 20 条" | 先读全部到内存再切 |
| 能给 `problem_id` 建索引吗 | **不能**，JSON 字段建不了索引 |
| 并发提交 | 两个请求改同一行 → **锁冲突** |

拆表后：

```sql
SELECT * FROM submission WHERE user_id = 3 ORDER BY create_time DESC LIMIT 20;
```

> **根本原则：一行里一个格子只能放一个值。放不下就必须拆表。**
> 正式名字叫 **第一范式（1NF）**，面试会问。

### 6.3 密码：BCrypt

**绝不能存明文。** 数据库一旦泄露（拖库），所有密码直接暴露；很多人跨站复用密码，等于连带毁掉别人的账号。

#### ① 为什么是 BCrypt

BCrypt 是**专门为安全存储密码设计的单向哈希函数**——不是加密，哈希后无法还原明文。

核心思想：**故意变慢**，提高暴力破解成本。

| 方案 | 安全吗 | 为什么 |
|---|---|---|
| `MD5(password)` | ❌ | 彩虹表直接反查；GPU 每秒 10¹⁰ 次 |
| `MD5(password + 全局盐)` | ❌ | 盐全局，一次算出全部 |
| `SHA256` + 每用户盐 | ⚠️ | 方案对，但**太快** |
| **BCrypt** | ✅ | 内置随机盐 + 可调成本因子 |

#### ② 两个核心设计

**自动加盐（Salt）**
- 每次哈希自动生成随机盐
- **同一密码每次生成的哈希不同**（这是正常的，不是 bug）
- 防御彩虹表

**可调成本因子（Cost Factor）**
- 决定迭代次数，每加 1，计算时间约翻倍
- 默认 `10`，即 2¹⁰ 次迭代
- 可根据硬件性能调高

#### ③ 哈希字符串格式

```text
$2b$10$7JB720yubVSZvUI0rEqK/.VqGOZTH.ulu33dHOiBE8ByOhJIrdAu2
```

| 部分 | 含义 |
|---|---|
| `$2b$` | 算法版本标识 |
| `10` | 成本因子，迭代 2¹⁰ 次 |
| 中间部分 | 随机盐值 |
| 最后部分 | 最终哈希值 |

**盐和成本因子都存哈希串里**，验证时不用额外查库。

#### ④ 字段长度为什么是 `VARCHAR(100)`

BCrypt 输出**固定 60 字符**。给 100 是留余量——万一以后换算法（加版本前缀）就溢出了。

#### ⑤ Java 里怎么用

```java
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();  // 默认成本因子 10

String hash = encoder.encode("123456");                 // 加密
boolean ok  = encoder.matches("123456", hash);          // 验证
```

**验证必须用 `matches()`，不能比较字符串**——因为盐不同，两次 `encode` 结果不一样。

> 备选方案 jBCrypt：`BCrypt.hashpw()` / `BCrypt.checkpw()`，原理相同。

#### ⑥ 注意事项

- 成本因子不是越高越好，默认 `10` 是安全起点，要在压测和登录延迟之间权衡
- BCrypt 输入密码有 **72 字节**上限，超出会被截断
- `matches()` 的原理：从存储的哈希里解析出盐和成本因子，对输入明文重新哈希再比对
- BCrypt 是单向哈希，**密码丢失只能重置，不能找回**

### 6.4 `create_time` / `update_time`：审计字段

| 字段 | 回答什么 | 谁用 |
|---|---|---|
| `create_time` | 什么时候注册的 | 排序、活动分析、数据修复 |
| `update_time` | 最后一次被改是什么时候 | **排查脏数据的第一手线索** |

```sql
create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

> 进阶：`update_time` 的升级版是**乐观锁** `version` 字段，D10 讲并发会用到。

### 6.5 唯一约束：两层都要（面试高频）

**只靠代码层会出什么事：**

```
请求 A：查 alice 存在吗？→ 不存在 ✓
请求 B：查 alice 存在吗？→ 不存在 ✓        ← 几乎同时
请求 A：INSERT alice                        ✅
请求 B：INSERT alice                        ✅
```

**数据库里有两条 `alice`。** 这叫 **check-then-act 竞态**：查的时候安全，动手的时候已经不安全。

| 层 | 职责 | 好处 |
|---|---|---|
| 代码层（先查一次） | 快速返回「用户名已存在」 | 体验好，省一次写 |
| 数据库层（`UNIQUE`） | **最后防线**，防并发 | 保证数据绝对正确 |

> **能靠数据库保证的正确性，不要只靠代码。**
> **代码负责"友好"，数据库负责"正确"。**

实现时还要 **catch `DuplicateKeyException`**——高并发下查重会漏，最终拦住它的是数据库。

### 6.6 软删除，以及「逻辑关系 ≠ 物理外键」

**为什么用 `status` 软删除**：真删用户后，他几百条 `submission` 要么跟着删（历史统计被篡改），要么留下悬空 `user_id`。软删除两个问题都解决。

**外键建不建，要分开看：**

| 关系 | 建外键吗 | 为什么 |
|---|---|---|
| `testcase → problem` | ✅ + `ON DELETE CASCADE` | 题目**真删**，测试点跟着删合理 |
| `submission → user` | ❌ 不建 | 用户**软删除**永不真删，外键没用；且提交表写入量极大，外键校验是写入开销 |

> **逻辑上有 1:N 关系 ≠ 物理上必须建外键。** 大厂经常故意不用外键。

### 6.7 索引：`UNIQUE` 本身就是索引

| 索引 | 加速的查询 | 接口 |
|---|---|---|
| `PRIMARY (id)` | `WHERE id = ?` | 所有按 ID 取用户 |
| `UNIQUE uk_username (username)` | `WHERE username = ?` | **登录**、注册查重 |
| `KEY idx_accepted (accepted_count)` | `ORDER BY accepted_count DESC` | 排行榜 |

> **`UNIQUE KEY` = 一个"不允许重复"的索引。** 建约束时索引自动就有了，不用为登录另建。

**不建的**：`nickname`（没人按它查）、`status`（只有 2 个值，区分度太低）。

## 八、实体类与 Mapper

### 8.1 `User.java`

```java
@Data
@TableName("user")
public class User {
    @TableId(type = IdType.AUTO)
    private Long id;
    private String username;
    private String password;
    private String nickname;
    private String email;
    private String avatar;
    private Integer role;
    private Integer submitCount;      // → submit_count
    private Integer acceptedCount;    // → accepted_count
    private Integer status;
    private LocalDateTime createTime; // → create_time
    private LocalDateTime updateTime;
}
```

| 注解 | 作用 | 补充 |
|---|---|---|
| `@Data` | 生成 getter/setter/toString/equals/hashCode | Lombok 是**编译期注解处理器**，不是运行期反射 |
| `@TableName("user")` | 告诉 MP 这张类对应哪张表 | 不写也行（类名默认转小写），显式更清楚 |
| `@TableId(type = IdType.AUTO)` | 哪个字段是主键 + 怎么生成 | `AUTO` = 交给数据库的 `AUTO_INCREMENT` |

**两条必须遵守的规则：**

1. **字段用包装类型**（`Integer` / `Long`），不用基本类型。数据库字段可能是 `NULL`，赋给 `int` 会 NPE。
2. **不需要给每个字段写 `@TableField`**，`map-underscore-to-camel-case` 会自动转换。

### 8.2 `UserMapper.java`

```java
@Mapper
public interface UserMapper extends BaseMapper<User> {
}
```

**整个文件 5 行，零方法，但你已经拥有：**

| 方法 | 生成的 SQL |
|---|---|
| `insert(user)` | `INSERT INTO user (...) VALUES (...)` |
| `selectById(1L)` | `SELECT ... WHERE id = ?` |
| `selectOne(wrapper)` | `SELECT ... WHERE <条件> LIMIT 1` |
| `selectCount(wrapper)` | `SELECT COUNT(*) WHERE <条件>` |
| `updateById(user)` | `UPDATE user SET ... WHERE id = ?` |
| `deleteById(1L)` | `DELETE FROM user WHERE id = ?` |

**「注解是元数据，读者决定何时生效」的实锤：**

> 启动时 MyBatis-Plus 用**反射**读 `User` 上的 `@TableName` / `@TableId`，
> 知道表名、主键、字段与列的对应关系，
> 然后**为这个接口动态生成实现类**。

**为什么必须是 `interface`：** MyBatis 的本质是「为接口动态生成实现类」。给 class 它没法干。

**`@Mapper` 干什么：** 注册进 Spring 容器。不加它，`UserServiceImpl` 里注入 `UserMapper` 会报找不到 Bean。（等价写法：启动类上加 `@MapperScan("com.oj.mapper")`。）

## 九、补充：Java 的 `instanceof`

> 今天顺带问到的。和数据库无关，但属于「今天新学」。

### 9.1 作用

判断一个对象引用是否指向某个类、接口或数组类型的实例，返回 `boolean`。

```java
obj instanceof Type
```

### 9.2 四种典型用途

```java
// ① 类型判断
if (obj instanceof String) { ... }

// ② 配合强转，避免 ClassCastException
if (obj instanceof String) {
    String s = (String) obj;
}

// ③ 判断是否实现某接口
if (obj instanceof List) {
    List<?> list = (List<?>) obj;
}

// ④ 判断数组类型
Object arr = new int[10];
if (arr instanceof int[]) { ... }
```

### 9.3 五个特点

- **`null instanceof 任意类型` 永远返回 `false`**（不会 NPE）
- 不能用于基本类型（`int` 不能 `instanceof Integer`）
- 如果编译器能确定类型**不可能兼容**，直接编译报错
- 判断的是**运行时类型**关系，包括父类、接口、数组
- **Java 16+ 支持模式匹配**，省掉强转：

```java
if (obj instanceof String s) {
    System.out.println(s.length());   // 直接用 s
}
```

### 9.4 与 `getClass()` 的区别

```java
obj instanceof Object;          // 子类实例也返回 true（继承关系）
obj.getClass() == Object.class; // 必须精确类型相同
```

> 一句话：`instanceof` 判「是不是这一类（含子类/实现类）」，`getClass()` 判「是不是恰好这一种」。
