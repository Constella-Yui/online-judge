### 1.2 字段

| 字段 | 类型 | 为什么需要 | 能不能不要 |
|---|---|---|---|
| `id` | `BIGINT UNSIGNED` AUTO_INCREMENT | 唯一标识一行，其他表靠它引用 | ❌ 不能 |
| `username` | `VARCHAR(32)` NOT NULL | 登录名，**唯一** | ❌ 不能 |
| `password` | `VARCHAR(100)` NOT NULL | 存 **BCrypt 哈希**（固定 60 字符），不是明文 | ❌ 不能 |
| `nickname` | `VARCHAR(32)` | 展示名，可改，可与 username 不同 | ✅ 可以（默认用 username） |
| `email` | `VARCHAR(128)` | 找回密码、通知 | ✅ 可以 |
| `avatar` | `VARCHAR(255)` | 头像 URL | ✅ 可以 |
| `role` | `TINYINT` DEFAULT 0 | 0 普通 / 1 管理员，控制管理接口 | ❌ 不能 |
| `submit_count` | `INT` DEFAULT 0 | 提交总数，列表页直接读 | ✅ 可以（能实时算） |
| `accepted_count` | `INT` DEFAULT 0 | 通过题数，**排行榜排序用** | ✅ 可以（能实时算） |
| `status` | `TINYINT` DEFAULT 1 | 1 正常 / 0 封禁，**软删除** | ❌ 不能 |
| `create_time` | `DATETIME` DEFAULT CURRENT_TIMESTAMP | 注册时间：排序、审计 | ❌ 不能 |
| `update_time` | `DATETIME` DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 最后修改时间：排查脏数据、增量同步 | ❌ 不能 |

#### ❌ 这里原来有个大错误：把 `submission` 当成了 `user` 的字段

原写法：

> `submission` | 复合结构，包含题号、语言、时间、测试结果 | 用户做题结果 | 不能

**而同一份文件的 1.5 关系写的是**：「一个 user 有多条 submission，外键建在 submission 这边」——**两句自相矛盾**。

**为什么不能放：** 一个用户可能提交过 500 次。

| 问题 | 后果 |
|---|---|
| 这一行会多长 | 500 条提交（含代码）→ **几 MB**，一个"用户"占半页纸 |
| 查昵称要读多少 | `SELECT nickname FROM user WHERE id=3` **被迫读全部 500 条提交** |
| 怎么查"最近 20 条" | 只能先读全部到内存再切 |
| 能给 `problem_id` 建索引吗 | **不能**，JSON 里的字段建不了索引 |
| 并发提交 | 两个请求改同一行 → **锁冲突** |

**拆表之后：**

```sql
SELECT * FROM submission WHERE user_id = 3 ORDER BY create_time DESC LIMIT 20;
```

只读 20 行，还能走索引。

**根本原则：**

> **一行里的一个格子，只能放一个值。**
> 如果一个用户有多条提交，`user` 表物理上就放不下——不是"不该放"，是"放不下"。必须拆表 + 外键。
> 正式名字叫 **第一范式（1NF）**，面试会问。

### 1.3 五个设计决策，逐条讲清楚

#### ① 密码存什么，长度为什么是 100

**绝不能存明文。** 数据库一旦泄露（拖库），所有密码直接暴露；很多人跨站复用密码，等于连带毁掉别人的账号。

| 方案 | 安全吗 | 为什么 |
|---|---|---|
| `MD5(password)` | ❌ | 彩虹表直接反查；GPU 每秒算 10¹⁰ 次 |
| `MD5(password + 全局盐)` | ❌ | 盐是全局的，一次算出全部 |
| `SHA256` + 每用户随机盐 | ⚠️ 勉强 | 方案对，但**太快**，暴力破解仍可行 |
| **BCrypt** | ✅ | 自带随机盐 + 故意慢 |

**BCrypt 的两个关键点：**

1. **自带随机盐，且盐存在哈希串里** → **同一密码加密两次结果不同**，这是正常的。
2. **故意慢**：算一次约 100ms。登录时无感；攻击者要试 10 亿次密码就是 3 年。

BCrypt 输出固定 60 字符：

```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
```

**长度给 `VARCHAR(100)`** —— 留余量。不能给 60 整，万一以后换算法（加版本前缀）就溢出了。

> 验证要用 `matches(明文, 哈希)`，不能比较字符串。

#### ② `accepted_count` 存字段，还是每次算

**结论：存字段。**（这一条一开始就答对了）

自己的推理：*"每次算需要暴力扫描该用户所有正确提交，还要去重，不如存字段；存字段要在做对题目后更新，前提是做好同题目多次 AC 的去重。"*

**补充代价**：存字段 = 数据冗余，就有**不一致**的风险。
- 更新失败、事务回滚、并发更新都可能让计数漂移
- 所以要么放在同一事务里（和 `submission` 落库一起提交）
- 要么接受"轻微不准"，定期跑一次校准（用 `submission` 表重算）

**这是缓存/冗余字段的通用权衡：读性能 vs 一致性。**

#### ③ 为什么需要 `create_time` 和 `update_time`

这不是"统计用"的字段，是**审计**字段。

| 字段 | 回答什么 | 谁用 |
|---|---|---|
| `create_time` | 这个人**什么时候注册的** | 排序（最新注册）、活动分析、数据修复 |
| `update_time` | 这个人**最后一次被改是什么时候** | 排查脏数据、定位谁改的、增量同步 |

**最实用的场景：出 bug 时。** 线上发现一个用户权限错了，第一句话是"这条数据什么时候被改的？"——没有 `update_time` 只能猜。

**自动维护写法：**

```sql
create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

- `DEFAULT CURRENT_TIMESTAMP`：插入时不写，自动填当前时间
- `ON UPDATE CURRENT_TIMESTAMP`：**任何字段被改，自动刷新**

> 面试延伸：`update_time` 的进阶用法是**乐观锁**。真实项目里更常用 `version` 整数——每次更新 `version = version + 1`，更新时带上旧 version 做条件，不匹配说明被人改过。D10 讲并发会用到。

#### ④ 用户名唯一约束放哪层（面试高频）

**只靠代码层会出什么事：**

```
请求 A：查 alice 存在吗？→ 不存在 ✓
请求 B：查 alice 存在吗？→ 不存在 ✓        ← 几乎同时
请求 A：INSERT alice                        ✅
请求 B：INSERT alice                        ✅
```

**数据库里有两条 `alice`。** 代码逻辑本身没 bug，是**并发**打败了"先查后插"。

这叫 **check-then-act 竞态**：查的时候安全，动手的时候已经不安全了。

**加上数据库层 `UNIQUE`：** 请求 B 的 INSERT 被拒绝，抛 `DuplicateKeyException`。

**所以正确答案是：两层都要，各管一半。**

| 层 | 职责 | 好处 |
|---|---|---|
| **代码层**（先查一次） | 快速返回「用户名已存在」 | 省一次无谓的写，体验好 |
| **数据库层**（`UNIQUE`） | **最后防线**，防并发 | 保证数据绝对正确 |

**两句口诀：**

> **能靠数据库保证的正确性，不要只靠代码。**
> **代码负责"友好"，数据库负责"正确"。**

落实到 `UserServiceImpl`：先 `selectCount` 查重给友好提示，**同时 catch 住 `DuplicateKeyException`** 转成同样的错误提示——高并发下查重会漏，最终拦住它的是数据库。

#### ⑤ 为什么用 `status` 软删除

原始答案：*"用户还可以被解封，数据删除后无法恢复。"* —— **对，但只说到一半。**

**更重要的理由：历史数据的完整性。**

用户被删了，他 `submission` 表里那几百条记录怎么办？
- 跟着删？那这道题的通过率统计就变了，历史被篡改
- 留着？`user_id` 指向一个不存在的用户，成了**悬空引用**

**软删除（`status = 0`）两个问题都解决了**：数据还在，统计没错，人不能登录。

### 1.4 索引

> 硬标准：**每个索引都要写出一条它加速的 SQL。写不出来 = 不该建。**

| 索引 | 它加速哪条查询 | 这条查询在哪个接口里 |
|---|---|---|
| `PRIMARY (id)` | `SELECT ... FROM user WHERE id = ?` | 所有按 ID 取用户的地方 |
| `UNIQUE uk_username (username)` | `SELECT id, password FROM user WHERE username = ?` | **登录**、注册查重 |
| `KEY idx_accepted (accepted_count)` | `SELECT ... ORDER BY accepted_count DESC LIMIT 50` | **排行榜** |

#### 💡 关键巧劲：`UNIQUE` 本身就是索引

原答案只想到「登录频繁，需要加速」，但没发现：

> **`UNIQUE KEY uk_username (username)` = 一个"不允许重复"的索引。**
> 建唯一约束的同时，索引自动就有了，**不用为登录额外建任何东西。**

一份工作，两件事：既防重复注册，又加速登录查询。

#### 什么**不**建索引

- `nickname`：没人在按昵称查。**索引为查询而建，不为"看起来重要"而建。**
- `status`：基数只有 2 个值（0/1），区分度太低，索引没用
- 已有 `uk_username`，就不需要再单独建 `(username)`——前缀重复

> 「查看我的提交记录」需要索引，但那是 **`submission` 表**的事，不在这里。

### 1.5 关系

原始答案（**正确**）：

> 一个 user 有多条 submission，同一条 submission 只能由一个 user 产生。外键建在 submission 这边。

**1:N 关系，外键放在"多"的那一侧。** ✅

**但「要不要真的建外键」是另一回事**——对比一下：

| 关系 | 建外键了吗 | 为什么 |
|---|---|---|
| `testcase → problem` | ✅ 建了 + `ON DELETE CASCADE` | 题目是**真删**（下架），测试点跟着删才合理 |
| `submission → user` | ❌ **不建** | 用户是**软删除**，永远不真删，外键没有用处；且 `submission` 写入量极大，外键校验是额外的写入开销 |

**结论：逻辑上有 1:N 关系 ≠ 物理上必须建外键。**
外键是"数据完整性"和"写入性能"之间的权衡，大厂经常故意不用。

> 差异不是错，是盲区。**对不上的地方才是今天真正学到的东西。**

| # | 我的设计 | 原 schema | 差异 | 谁对？为什么 |
|---|---|---|---|---|
| 1 | `submission` 作为 user 的一个字段 | `submission` 是独立表，通过 `user_id` 关联 | ❌ 严重 | schema 对：一行放不下多个值，必须拆表（1NF） |
| 2 | `name` | `username` | 命名 | schema 对：`name` 太泛 |
| 3 | 字符数组 | `VARCHAR(n)` | 类型 | schema 对：SQL 里是变长字符串，要指定上限 |
| 4 | `status BOOLEAN` | `status TINYINT` | 类型 | schema 对：MySQL 的 `BOOLEAN` 只是 `TINYINT(1)` 的别名 |
| 5 | 无 `id` 主键 | `id BIGINT UNSIGNED AUTO_INCREMENT` | ❌ 缺失 | schema 对：每张表必须有主键 |
| 6 | 无时间字段 | `create_time` / `update_time` | ❌ 缺失 | schema 对：审计字段，排查问题的第一手线索 |
| 7 | `accept_count` | `accepted_count` | 拼写 | schema 对：与 `submit_count` 对称 |
| 8 | 索引只想到"登录要加速" | `UNIQUE uk_username` 本身就是索引 | 盲区 | **一份工作两件事**：唯一约束顺手解决了查询性能 |
| 9 | 未提 `idx_accepted` | 排行榜排序需要 | 遗漏 | 排序字段要考虑索引，否则 `filesort` |

**统计**：
- 我多想的（原 schema 没有的）：无
- 原 schema 多想的（我没想到的）：主键、两个时间字段、排行榜索引、UNIQUE=索引
- 我判断原 schema 有问题的：无

## A.3 当时不懂、现在必须能讲的四个

1. **密码为什么用 BCrypt 而不是 MD5/SHA256？**（§1.3 ①）
   → 自带随机盐 + 故意慢。同一密码两次加密结果不同是正常的。

2. **唯一约束为什么要数据库层和代码层都做？**（§1.3 ④）
   → 代码层防"体验"，数据库层防"并发"。`check-then-act` 竞态下，查重会漏。

3. **`create_time` / `update_time` 到底谁用？**（§1.3 ③）
   → 审计。线上出问题时"这条数据什么时候被改的"是第一手线索。

4. **索引怎么建？**
   → 唯一标准：**写得出它加速的那条 SQL**。`UNIQUE` 自带索引，别再重复建。

## A.4 一句话总纲

> **一行一个格子只能放一个值 → 放不下就拆表。**
> **唯一约束顺手就是索引，别重复建。**
> **代码管友好，数据库管正确。**
