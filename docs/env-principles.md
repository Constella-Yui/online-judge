## 1. 环境变量：JAVA_HOME 与 PATH

### 1.1 环境变量是"进程继承"的

你在 PowerShell 里敲命令，这个 PowerShell 进程有一份**自己的**环境变量副本。它来自哪里？

```
你登录 Windows → explorer.exe 启动 → 你双击 PowerShell → 新进程复制 explorer 的环境变量
最终源头：注册表里的"系统变量"(Machine) + "用户变量"(User)
```

**关键结论：改了环境变量，已经开着的终端不会更新。必须关掉重开。** 今天你改完 PATH 要新开窗口才生效，就是这个原因。

> 顺带解释一个今天的现象：我这边跑 `java -version` 一直看到旧版本，是因为我的 shell 继承的是 Claude Code 启动那一刻的环境。所以我是直接读注册表看的真实值：
> 🖥️【本机】`powershell -NoProfile -Command "[Environment]::GetEnvironmentVariable('Path','Machine')"`
> 这就是"看到的 ≠ 真实配置"时的排查手段。

### 1.2 PATH 的查找规则：第一个命中即返回

PATH 是一串用 `;` 分隔的目录。你敲 `java`，Windows 沿着这串目录**从左到右**找 `java.exe`，**找到第一个就执行，不再往后看**。

所以：**谁排前面谁赢。**

Windows 拼出来的完整 PATH 顺序是：

```
[系统变量 Path 的全部内容] ; [用户变量 Path 的全部内容]
```

系统在前，用户在后。

想看实际命中哪个，用：

🖥️【本机】`where java`

它会按 PATH 顺序把**所有**叫 `java.exe` 的路径都列出来，第一个就是实际执行的那个。

### 1.3 今天到底出了什么问题

现象：`java -version` 是 1.8，`javac -version` 是 25，`mvn -v` 又是 25。三个命令，三个答案。

原因：机器上装了**三套** Java 入口，而它们互相不说话：

| 入口 | 里面有什么 |
|---|---|
| `C:\Program Files (x86)\Common Files\Oracle\Java\javapath`（Oracle Java 8 的"快捷方式目录"） | **只有** `java.exe` `javaw.exe` `javaws.exe`，**没有 `javac.exe`** |
| JDK 25 的 `bin` | 全套 |
| JDK 21 的 `bin` | 全套 |

于是：`java` 命中 javapath → 报 1.8；`javac` 在 javapath 里找不到 → 继续往后 → 命中 JDK 25 → 报 25。

**这就是"版本不一致"的典型来源**：不是装错了，是 PATH 里排了多个入口，不同命令命中了不同目录。

### 1.4 JAVA_HOME 是干什么的

JAVA_HOME 是**约定俗成的变量**，JDK 自己根本不认它。认它的是**别人**：

- Maven（`mvn -v` 显示的 Java 版本来自 JAVA_HOME）
- IntelliJ IDEA
- Tomcat、各种 `.bat` 脚本

所以规则是：**`java` 走 PATH，`mvn` 走 JAVA_HOME。** 两者不一致就会出现"`java` 是 21 但 `mvn` 用 25"。

正确的做法是**两者指向同一个 JDK**，并且把 `%JAVA_HOME%\bin` 放在 PATH 最前面——这样改 JAVA_HOME 一处，PATH 自动跟着变，不会再打架。

### 1.5 为什么 Java 这么麻烦，C++ 不这样

你用 g++/clang 时，编译器装在哪、标准库在哪，通常有固定位置和自带的查找机制。JDK 不一样，可以随便解压到任何目录（你的就是 `D:\dev\jdk-21.0.13+9`，一个纯 zip 解压出来的文件夹），所以需要一个"指路牌"告诉所有工具它在哪里。JAVA_HOME 就是这个指路牌。

### 1.6 为什么编译器版本必须和运行时匹配

Java 编译产物 `.class` 文件开头有一个**版本号**（major version）。JVM 加载时会检查：**运行时的 JVM 版本必须 ≥ 编译时的版本**，否则抛：

```
java.lang.UnsupportedClassVersionError:
  class file version 65.0, this version of the Java Runtime only recognizes class file versions up to 61.0
```

| JDK | class 文件 major version |
|---|---|
| 8 | 52 |
| 11 | 55 |
| 17 | 61 |
| 21 | 65 |
| 25 | 69 |

这就是"高版本编译、低版本运行"必然失败的物理原因。

**和项目的关系**：Spring Boot 3.x 最低要求 JDK 17。所以 JDK 21 不是随便选的，是这个技术栈的下限。

## 2. Docker 资源限制：判题沙箱的实体

### 2.1 为什么判题必须隔离

用户提交的是**任意代码**。可能是：

- `while(true);` —— 死循环吃满 CPU
- `while(1) fork();` —— fork 炸弹，几秒钟撑爆进程表，整台机器失联
- `open("/etc/passwd")` —— 偷看服务器文件
- 直接连外网下载挖矿程序

不隔离 = 把你的服务器交给陌生人随便玩。所以**判题沙箱是 OJ 项目最核心、面试问得最狠的部分**。

### 2.2 四道闸门

`docker run` 的这几个参数，一个一个对应一类风险：

| 参数 | 挡什么 | 超了会怎样 |
|---|---|---|
| `--memory=256m` | 内存炸弹（`new int[1<<30]`、无限申请） | 内核 OOM killer 杀掉进程，**退出码 137** |
| `--cpus=1.0` | CPU 抢占（死循环） | 只拿到 1 核的时间片，其他容器不受影响；配合自己的计时判 TLE |
| `--pids-limit=64` | fork 炸弹 | 第 65 次 fork 失败，进程创建被拒 |
| `--network=none` | 偷数据、外连、挖矿回连 | 容器里没有任何网络接口，连 DNS 都解析不了 |

再加一层文件系统：

- `--read-only` 让整个容器根文件系统只读
- 只把用户代码和测试数据目录挂进去：`-v /tmp/sub_123:/box`
- 编译产物也写在 `/box` 里

完整形态大致是：

🌐【服务器】
```bash
docker run --rm \
  --memory=256m --cpus=1.0 --pids-limit=64 --network=none \
  -v /tmp/sub_123:/box \
  gcc:13 \
  sh -c 'cd /box && g++ -O2 main.cpp -o a.out && ./a.out < input.txt'
```

### 2.3 退出码体系（面试常问，要能背）

进程被信号杀掉时，shell 报告的是 `128 + 信号编号`：

| 退出码 | 含义 |
|---|---|
| `0` | 正常结束 |
| `1` ~ `125` | 程序自己 return 的退出码 |
| `124` | `timeout` 命令超时（如果你用 coreutils 的 timeout 包一层） |
| **`137`** | `128 + 9`，SIGKILL —— **被 OOM 杀了 / 被强制杀死** |
| **`139`** | `128 + 11`，SIGSEGV —— **段错误**（C++ 常见的数组越界、野指针） |

判题结果映射就靠这个：

```
137 → Memory Limit Exceeded（也可能是被 timeout 强杀，要结合自己的计时区分）
139 → Runtime Error (Segmentation Fault)
其他非 0 → Runtime Error
超时（自己计时判断）→ Time Limit Exceeded
```

⚠️ **注意 TLE 通常不是靠退出码判的**。你自己记录开始/结束时间（或用 `timeout` 包一层），超了就是你判 TLE，然后把容器 kill 掉。

### 2.4 两个实战坑

**坑一：容器冷启动 500–800ms。** Docker 起容器不是免费的。一道题 20 个测试点，每个点起一次容器 = 十几秒，用户等得不耐烦，判题机也被拖死。这也是 OJ 性能优化的经典题目——解法是**容器预热 / 容器池**（预先起好 N 个容器待命）。这件事可以直接写进简历。

**坑二：`--memory` 限制的是容器总内存，包括编译器。** `g++ -O2` 编译大文件本身要吃掉 100M+。如果 memory 设成 128M，可能编译阶段就被 OOM 了。所以**编译和运行要分开限制**——编译给宽松（512M），运行给严格（题目限制的 MB + 一点余量）。

## 3. SSH 隧道：为什么数据库不暴露公网

### 3.1 127.0.0.1 意味着什么

`127.0.0.1` 是**回环地址**，永远指向"我自己"。它只在机器内部有效，外网永远连不到。

我们在 `docker-compose.yml` 里写的是：

```yaml
ports: ["127.0.0.1:3306:3306"]
```

意思是：Docker 只把 MySQL 的端口发布到**服务器的回环地址**上。于是：

- 服务器自己 → `127.0.0.1:3306` ✅ 通
- 你从家里直接连 `47.243.5.119:3306` ❌ 不通

### 3.2 为什么必须这样

MySQL 一旦暴露公网，全世界 24 小时都在扫 3306 端口，用字典爆破 root 密码。历史上无数服务器就是这么变成挖矿机的。**数据库只绑回环地址是安全基线，不是可选优化。**

### 3.3 隧道怎么把"不通"变成"通"

🖥️【本机】
```bash
ssh -N -L 3306:127.0.0.1:3306 \
       -L 6379:127.0.0.1:6379 \
       -L 5672:127.0.0.1:5672 \
       -L 15672:127.0.0.1:15672 \
       root@47.243.5.119
```

拆开看 `-L 3306:127.0.0.1:3306`：

| 位置               | 含义                  |
| ---------------- | ------------------- |
| `-L`             | local forward（本地转发） |
| 第一个 `3306`       | **你本机**上要监听的端口      |
| `127.0.0.1:3306` | **从服务器视角**看，要连的目标   |

记忆格式：**`-L 本地端口:目标主机:目标端口`**，目标主机和端口是从**服务器那边**看的世界。

流量路径：

```
IDEA 里配 localhost:3306
      ↓
本机 3306（ssh 进程在听）
      ↓  ══ SSH 加密通道 ══
服务器 127.0.0.1:3306（MySQL）
```

所以 IDEA 里填 `localhost:3306` 就能连上，因为在你本机看它就是本地端口。而服务器视角看这个 MySQL 连接**来自它自己的 localhost**——完全看不出来自外网。

### 3.4 三个注意点

1. **`-N`** 表示"不执行远程命令"，只做转发。不加的话会给你一个 shell 然后通道行为不一样。
2. **本地不能同时跑 MySQL**，否则 3306 被占，隧道起不来（`bind: Address already in use`）。
3. 隧道窗口**关掉就断**。IDEA 报"连接超时"先看隧道是不是关了。

## 4. MySQL 参数：3.4G 内存下的取舍

### 4.1 三个关键参数

```yaml
command:
  - --innodb-buffer-pool-size=256M
  - --performance-schema=OFF
  - --character-set-server=utf8mb4
  - --default-time-zone=+08:00
```

**`innodb_buffer_pool_size`** —— InnoDB 的内存缓存池。缓存数据页和索引页，查询先查缓存，命中就不读磁盘。

- 默认 128M
- 官方建议物理内存的 50%–70%（大库）
- 你的情况：3.4G 还要养 Redis 和 RabbitMQ，**只能给 256M**

一句话总结这场取舍："内存只有 3.4G，MySQL 占大头但必须给中间件留活路，所以把 buffer pool 压到 256M，代价是缓存命中率低、小规模够用。"

**`performance_schema=OFF`** —— MySQL 自带的性能监控模块，采集大量运行时指标，开销约 100–200M。开发和中小规模关掉；生产大库要开（排查慢查询要靠它）。

**`--default-time-zone=+08:00`** —— 容器默认是 **UTC**。不设的话，`create_time` 存进去和你本地看到的差 8 小时。这是 Java + MySQL 时区问题的经典坑，Java 侧的 JDBC URL 还要配套写 `serverTimezone=Asia/Shanghai`。

**`--character-set-server=utf8mb4`** —— MySQL 里的 `utf8` 是**假的 UTF-8**，最多 3 字节，存不了 emoji 和部分生僻字。`utf8mb4` 才是真的。这是 MySQL 特有的历史包袱，面试爱问"utf8 和 utf8mb4 有什么区别"。

### 4.2 怎么验证

🌐【服务器】
```bash
docker stats --no-stream
```

`--no-stream` 是"只打印一次就退出"。不加的话它实时刷新刷新，占住终端，得按 `Ctrl+C`。

## 5. 扫一眼就够的三件事

### 5.1 SSH 密钥对

**非对称加密**：一对钥匙。公钥（`.pub`）可以随便给全世界，私钥必须自己藏着。

登录流程：

1. 你预先把自己的公钥放到服务器 `~/.ssh/authorized_keys`
2. 登录时服务器发一段**随机挑战**
3. 你用自己的私钥对挑战签名
4. 服务器用你的公钥验签，对了就放行

**私钥全程不传输**——这就是它比密码强的地方：密码要在网络上传输、可能被猜、可能被暴力破解；私钥不出本地，服务器只存公钥，即使服务器被拖库也拿不到你的钥匙。

> ⚠️ `~/.ssh/id_ed25519` 是私钥，**永远不要发给任何人、不要截图、不要贴到对话里**。`id_ed25519.pub` 才是可以公开的。

### 5.2 Maven 镜像

Maven 从 Maven Central（美国）下依赖，走 HTTP，国内很慢。`~/.m2/settings.xml` 里的 `<mirror>` 把 `central` 指向阿里云镜像，等于换源。

和 pip 用清华源、npm 用淘宝源是同一件事。**注意**：我们项目里 Spring Boot 3.5.16 从阿里云能正常下（日志里 `Downloaded from aliyun-public` 就是证据）。

### 5.3 git 用 SSH 而不是 HTTPS

两种远程地址的区别只在**认证方式**：

- `git@github.com:user/repo.git` —— 走 22 端口，用 SSH 密钥认证，配一次以后不用管
- `https://github.com/user/repo.git` —— 走 443 端口，用账号 + token 认证，不配 credential helper 就要每次输

没有性能差别，SSH 只是省事。

## 6. 完全不用管的

| 事 | 只需记住一句 |
|---|---|
| DISM / sfc / CBS 修复 | Windows 组件存储损坏时，跑 `DISM /Online /Cleanup-Image /RestoreHealth` 修。**知道这句就够了** |

**这些是踩坑后的修复动作，不是知识。** 面试官不会问你怎么修 Windows，也不会问你为什么 IDE 向导难用。

## 附录 C：自测题参考答案

> 每条先给「一句话答案」（面试就这么答），再给「展开」（自己理解用）。
> 自评标准：**能不看答案说出那句话 = 过关**；只能说得出展开里的细节、说不出那句话 = 还没真正懂。

### 1. 为什么改完环境变量，已经开着的 PowerShell 里 `java -version` 还是旧的？

**一句话**：环境变量是进程**启动时复制的一份快照**，不会实时同步。已经开着的终端拿到的是它启动那一刻的旧副本。

**展开**：你改环境变量，改的是注册表（源头）。新进程的环境变量从父进程继承，一路往上追溯到注册表——但**只在进程创建的那一刻复制一次**。所以必须关掉重开，让 Windows 重新读一遍注册表。

**排查手法**：拿不准自己看到的是不是真实配置时，直接读注册表：

🖥️【本机】
```bash
powershell -NoProfile -Command "[Environment]::GetEnvironmentVariable('Path','Machine')"
```

看到的是源头，而不是某个进程里的陈旧副本。

---

### 2. 机器上同时有 JDK 8 / 21 / 25，`java` 和 `javac` 显示不同版本，可能是什么原因？

**一句话**：PATH 里有多个 Java 入口，`java.exe` 和 `javac.exe` **命中了不同的目录**。

**展开**：Windows 沿 PATH 从左到右找第一个匹配，找到就停。Oracle 装的 `javapath` 目录里**只有** `java.exe` `javaw.exe` `javaws.exe`，**没有 `javac.exe`**。于是：

- `java` → 在 javapath 命中 → 报 1.8
- `javac` → javapath 里找不到 → 继续往后 → 命中 JDK 25 → 报 25

补充一条容易被忽略的：Windows 拼出来的完整 PATH 是 **系统 Path + 用户 Path**，系统在前。所以用户变量里排得再靠前，也压不过系统变量里的条目。

**排查手法**：

🖥️【本机】`where java` / `where javac`

会把所有命中的路径**按 PATH 顺序**列出来，第一个就是实际执行的那个。

### 3. `JAVA_HOME` 是谁在读？为什么 `java` 对了 `mvn` 还可能不对？

**一句话**：JAVA_HOME 是**给其他工具看的指路牌**，JDK 自己根本不读它。读它的是 Maven、IDEA、Tomcat 和各种 `.bat` 脚本。

**展开**：`java` 命令走的是 **PATH 查找**；`mvn` 启动时读 **JAVA_HOME** 决定用哪个 JDK。这是两条独立的路径，可以指向不同的 JDK，互不干涉。所以"`java -version` 是 21，`mvn -v` 却显示 25"完全可能。

**正确做法**：让 JAVA_HOME 指向目标 JDK，并把 `%JAVA_HOME%\bin` 放在 PATH **最前面**。这样改一处，两边跟着一起变，天然不会打架。

---

### 4. 用 JDK 21 编译的 class 能在 JDK 17 上跑吗？报什么错？

**一句话**：**不能**，抛 `UnsupportedClassVersionError`。

**展开**：`.class` 文件头带一个 major version。JVM 加载时要求 **运行时版本 ≥ 编译时版本**：

| JDK | major version |
|---|---|
| 17 | 61 |
| 21 | 65 |

21 编出的是 65，17 的 JVM 最多认到 61，直接拒绝加载，报错信息里会写 `class file version 65.0, this version of the Java Runtime only recognizes class file versions up to 61.0`。

**反向可以**：JDK 17 编的（61）能在 JDK 21 上跑——新 JVM 认得旧 class。

**加分点**：想让 JDK 21 编出能在 17 上跑的 class，用 `javac --release 17`。这是跨版本兼容的标准做法，Maven 里对应 `maven.compiler.release` 配置。

### 5. 判题时容器的退出码是 137，说明发生了什么？

**一句话**：`137 = 128 + 9`，进程被 **SIGKILL** 强杀了；判题场景里最典型的原因是**内存超限**，被内核 OOM killer 干掉。

**展开**：进程被信号杀死时，shell 报告 `128 + 信号编号`。9 号是 SIGKILL——不可捕获、不可忽略，进程没有任何机会善后，直接被抹掉。这就是为什么"内存超限"能靠退出码判定：内核杀进程既快又干净。

**判题里必须注意的坑**：137 **不能一见到就判 MLE**。`timeout` 命令超时强杀、运维手动 `docker kill`，退出码也是 137。所以要结合**自己的计时和内存统计**区分：

```
超时（自己计时判断）              → TLE
内存统计超限 / 容器 cgroup 报 OOM → MLE
其他非 0 且未超时                 → RE
```

### 6. `--pids-limit=64` 挡的是哪种攻击？不挡会怎样？

**一句话**：挡 **fork 炸弹**——一段 `while(1) fork();` 会在几秒内耗尽系统进程表的 PID 空间，让整台机器连 SSH 都登不上。

**展开**：Linux 每个进程都要占一个 PID，上限通常几万个。用户提交的是**任意代码**，一个恶意提交就能给判题机造成 DoS——这不是理论问题，是被玩烂的攻击手法。

`--pids-limit=64` 让容器内进程数到达上限后，`fork()` 直接失败返回 `EAGAIN`，影响**被限制在容器内部**，宿主机和其他判题容器毫发无伤。

**顺带记住另外三道闸门**：`--memory`（内存炸弹）、`--cpus`（死循环抢 CPU）、`--network=none`（外连偷数据）。四个参数合起来，才构成简历上"基于 Docker 的判题沙箱隔离"这句话。

### 7. 为什么 MySQL 只绑 `127.0.0.1`？那你本地怎么连？

**一句话**：`127.0.0.1` 是回环地址，外网根本没有路由能到它，等于**只允许本机访问**——防止数据库被公网爆破。本地通过 **SSH 隧道**连。

**展开**：3306 是全网扫描的头号目标之一。一旦暴露公网，24 小时都有人在用字典爆破 root 密码；弱口令被攻破后，服务器通常几分钟内变成挖矿机。**数据库只绑回环地址是安全基线，不是可选的优化。**

**本地连法**：

🖥️【本机】
```bash
ssh -N -L 3306:127.0.0.1:3306 root@47.243.5.119
```

然后在 IDEA / Navicat 里照常配 `localhost:3306`——在你本机看，它就是本地端口。

---

### 8. `ssh -L 3306:127.0.0.1:3306` 里，两个 `3306` 分别是谁的端口？

**一句话**：**第一个是本机的**监听端口，**第二个是目标端口**；中间的 `127.0.0.1` 要**从服务器视角**理解——它指服务器自己。

**展开**：格式是 `-L 本地端口:目标主机:目标端口`。目标那一侧的"世界"是**服务器的**世界，所以 `127.0.0.1` 是服务器自己的回环地址。

```
IDEA 配 localhost:3306
      ↓
本机 3306（ssh 进程在监听）
      ↓  ══ SSH 加密隧道 ══
服务器 127.0.0.1:3306（MySQL）
```

所以服务器看到的这个 MySQL 连接**来自它自己的 localhost**，完全看不出是从外网隧道过来的——这正是隧道能绕过安全限制的原理。

**两个实战坑**：

- 本机不能同时跑一个 MySQL 占着 3306，否则隧道起不来（`bind: Address already in use`）
- 隧道窗口一关，连接立刻断，IDEA 报超时会让人以为是数据库挂了

### 9. `innodb_buffer_pool_size` 是什么？为什么你这个项目只敢给 256M？

**一句话**：InnoDB 的**内存缓存池**，缓存数据页和索引页，查询先查它，命中就不读磁盘。只给 256M 是因为**服务器总共只有 3.4G 可用内存，还要同时养 Redis 和 RabbitMQ**。

**展开**：这是 MySQL 最重要的性能参数。默认 128M，官方对专用数据库服务器建议物理内存的 50%–70%——因为内存和磁盘差了几个数量级的速度，缓存命中率直接决定 QPS。

你的机器 3.4G 可用内存，三个中间件并排跑：

| 组件 | 占用 |
|---|---|
| MySQL | buffer pool 256M + 连接/其他开销 |
| Redis | `maxmemory 128mb` |
| RabbitMQ | 水位 0.4 |

给 MySQL 独占一半，另外两个就会 OOM，整机崩。所以这是**主动的取舍**：牺牲缓存命中率换整机稳定——项目数据量很小，256M 绰绰有余。

**面试怎么说**：不要背参数，讲这个取舍：

> "我服务器只有 3.4G 内存，同时跑 MySQL/Redis/RabbitMQ。我把 InnoDB buffer pool 压到 256M、关掉 performance_schema，Redis 限 128M，RabbitMQ 水位设 0.4。这是牺牲单库性能换整机可用性，项目数据量小，命中率不是瓶颈。"

有理由的取舍，比背下来的参数值值钱得多。

### 10. MySQL 的 `utf8` 和 `utf8mb4` 有什么区别？

**一句话**：MySQL 的 `utf8` 是**残缺的 UTF-8**，最多 3 字节，存不了 4 字节字符（emoji、部分生僻字）；`utf8mb4` 才是**完整的** UTF-8，最多 4 字节。

**展开**：这是 MySQL 的历史包袱。早年为了省空间搞了个 3 字节版本，还起了个误导性的名字叫 `utf8`。后来发现 Unicode 里有 4 字节的字符（emoji 就是典型），只能再补一个真 UTF-8，命名为 `utf8mb4`（mb4 = **m**ost **b**ytes **4**）。

所以结论很干脆：

> **永远用 `utf8mb4`。`utf8` / `utf8mb3` 一律不用。**

配套还要一起设，否则照样出问题：

- 字符集：`character-set-server=utf8mb4`
- 排序规则：`utf8mb4_unicode_ci`
- 连接层（JDBC URL）：`useUnicode=true&characterEncoding=utf8`

**面试为什么会问**：因为无数线上事故是"建库时用了 `utf8`，上线后用户昵称带 emoji 直接 500"。这是个能立刻判断你有没有真实工程经验的题。
